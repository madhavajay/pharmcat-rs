Star Alleles for Coders

How PharmCAT turns a VCF of variant calls into a diplotype like CYP2C19 *2/*17 — the data, the matching algorithm, when phasing matters, and whether you can drop in raw PharmVar data.

Grounded in the PharmCAT Java source under haplotype/ and the real *_translation.json definition files. File/line citations throughout.

The one-sentence version: there is no rule engine. Each star allele is stored as a vector of expected bases at a fixed list of positions; PharmCAT builds every possible haplotype string your sample could have, regex-matches those strings against every allele vector, pairs the matches into diplotypes, and ranks them by a score. "Filtering down to candidates by elimination" is exactly right — the rules are the data.

1. The mental model

A star allele (haplotype) is a named pattern of DNA at specific positions in one gene — e.g. CYP2C19*2. You have two copies of each gene (maternal + paternal), so your genotype is a diplotype: two star alleles, e.g. *2/*17. That diplotype maps to a metabolizer phenotype (poor / intermediate / normal / rapid / ultrarapid), which drives a dosing recommendation.

The pipeline has three independent data layers. PharmCAT's matcher only does the first arrow:

VCF variant calls ──▶ DIPLOTYPE        (the "matcher" — this guide)
diplotype         ──▶ PHENOTYPE        (phenotypes.json — allele function/activity scores)
phenotype + drug  ──▶ RECOMMENDATION   (prescribing_guidance.json — CPIC/DPWG/FDA)

Keep these separate in your head. A gene can be perfectly callable at layer 1 and yet useless clinically because layers 2–3 don't exist for it. (That is the whole CYP1A2 / CYP2C8 story — see §9.)

2. Where the rules live (the data)

Each gene ships one definition file, e.g. CYP2C19_translation.json. It has two parts that matter:

(a) variants[] — the fixed list of positions this gene cares about

Every position is already normalized to genomic VCF coordinates (GRCh38), with a reference and alternate base:

{ "position": 94761900, "rsid": "rs12248560", "ref": "C", "alts": ["T"],
  "chromosomeHgvsName": "g.94761900C>T" }     // CYP2C19, chr10

(b) namedAlleles[] — each star allele as a parallel array of expected bases

The alleles array lines up 1:1 with variants[]. A value of null means "this allele doesn't constrain that position." Here is the real data (non-null entries only):

AllelePharmVar/PA idDefining calls (position → base)
*1PA165980634reference baseline — defines the "wild-type" base at the common positions
*2PA16598063594775367:G, 94775507:R, 94781859:A, 94842866:G

That table is the rule set. "*2 = G at 94775367 AND A at 94781859 AND …". No if/else anywhere — adding a gene means adding a file, not code.

3. The algorithm, step by step

Top-level orchestration lives in NamedAlleleMatcher.call(), which builds a MatchData per gene and hands it to DiplotypeMatcher.compute().

1
Read the sample's calls at the gene's positions. For each position in variants[], find the sample's genotype. Three outcomes: present (e.g. C/T), homozygous (T/T), or missing (no data).
MatchData constructor — maps position → SampleAllele; tracks missing positions.
2
Adapt the definitions to what the sample actually has. If the sample is missing a position, the named alleles are truncated to only the positions present (marshallHaplotypes()). Positions a definition leaves null are filled with the reference base (defaultMissingAllelesToReference()).
3
Generate every haplotype string the sample could carry. This is the key step. From the per-position calls, enumerate the possible single-chromosome sequences (generateSamplePermutations() → CombinationUtil.generatePermutations()). The number of permutations depends entirely on phasing (§6).
4
Match each permutation against every allele's pattern. Each permutation is a string like "94761900:T;94762706:A;…"; each allele is a compiled regex. A hit is a HaplotypeMatch (comparePermutations()).
5
Pair haplotype matches into diplotypes & validate. DiplotypeMatcher.compute() pairs matched haplotypes and keeps only complementary pairs: at a homozygous position both must agree; at a heterozygous position they must differ (isViableComplement()).
6
Score and rank. Each candidate diplotype gets a score = number of explicitly-defined positions it explains, minus penalties (wobble-collapsing-to-reference, partials). Sort descending; with topCandidateOnly, keep only the highest score. Ties ⇒ multiple reported diplotypes.

4. Alleles are regexes

At load time, NamedAllele.calculatePermutations() turns each allele's call vector into one compiled java.util.regex.Pattern over the full position list:

position defined as a base  ->  that base        "94775367:G"
IUPAC wobble (R = A or G)   ->  character class   "94775507:[AG]"
position left null          ->  wildcard          "94762706:.*?"

So *2 compiles to something like:

...;94775367:G;...;94775507:[AG];...;94781859:A;...;94842866:G;...

Matching is then literally pattern.matcher(permutationString).matches(). The wobble [AG] means *2 matches whether the sample shows A or G there — but a wobble that collapses to the reference base costs a scoring point, so a more specific allele wins ties.

5. Worked example: CYP2C19

Two of the positions in play:

  • 94761900 (rs12248560): ref C, alt T. The T defines *17.
  • 94781859 (rs4244285): the A defines *2. (Plus *2's other positions.)

Case A — homozygous / unambiguous

Sample is T/T at 94761900 and reference everywhere *2 needs. Every position is homozygous ⇒ only one distinct haplotype string ⇒ it matches *17 on both chromosomes. Result: *17/*17. No ambiguity, phasing irrelevant.

Case B — heterozygous at one allele's positions

Sample is C/T at 94761900, reference elsewhere. Two permutations: one chromosome carries T (→ *17), the other carries C (→ *1 reference). Complement check passes (they differ at the het position). Result: *1/*17. Still unambiguous, because only one position varies.

Case C — heterozygous at two alleles' positions (the interesting one)

Sample is heterozygous at the *17 position (C/T at 94761900) and heterozygous at a *2 position (G/A at 94781859). Now the question is cis vs trans:

ArrangementChromosome 1Chromosome 2Diplotype
trans (variants on opposite copies)T at 94761900 → *17A at 94781859 → *2*2/*17
cis (both variants on the same copy)T + A → a combined/other allelereference → *1*1/*(combo)

Both arrangements are consistent with the unphased genotype. Which one is real cannot be known from unphased calls — and that is precisely where phasing comes in.

6. Phasing: when it's used & when it can be skipped

PharmCAT never requires phased input. Phasing only changes how many permutations step 3 produces, which changes how many candidate diplotypes survive. The decision is per-sample, derived from the data:

// MatchData.generateSamplePermutations()
m_isEffectivelyPhased = (permutations.size() <= 2);
SituationPermutationsPhasing needed?
All positions homozygous (incl. all-reference)1No — only one possible haplotype
Heterozygous at ≤1 position≤2No — arrangement is forced
Input is phased (VCF GT uses |, e.g. 0|1, or carries PS phase sets)2Already resolved — follows the phase
Unphased & het at ≥2 positions2k (grows)Yes, to disambiguate cis/trans

The permutation generator branches on exactly this:

// CombinationUtil.generatePermutations(...)
if (allele.isEffectivelyPhased() || isHaploid) {
    // take ONE orientation — no branching
} else if (allele.getPhaseSet() != null) {
    // follow the phase set consistently (branch once per new PS)
} else {
    // UNPHASED het: branch BOTH ways (allele1-first AND allele2-first)
}
Skip phasing when the sample is homozygous everywhere, or heterozygous at only one position, or the genotype is already phased. In those cases the call is exact and identical to what phased data would give. The common case — homozygous reference at most positions — needs no phasing.
Phasing matters when the sample is unphased and heterozygous at two or more positions that belong to different alleles. Then PharmCAT enumerates both cis and trans and cannot prefer one on sequence alone.

7. Consequences of skipping phasing

If you feed unphased, multi-het data (the realistic case for most VCFs), here is what actually happens — none of it is silent:

  • Multiple candidate diplotypes are reported. Both *2/*17 and the cis alternative survive the complement check and tie on score, so PharmCAT returns all top-scoring diplotypes rather than guessing one. Downstream you may get a range of phenotypes.
  • Combination & "partial" alleles get fuzzier. Whether two variants are on the same strand determines if they form one combined allele or two separate ones (CombinationMatcher). Unphased, both readings are kept.
  • For some genes PharmCAT deliberately picks the conservative answer. Genes like CYP2D6 and DPYD use callLowestFunctionGene(): when phase is unknown, it assumes the arrangement that yields the lowest-function result, to avoid under-warning a poor metabolizer. Safe, but can over-call reduced function.
  • Phased input collapses the ambiguity. Provide 0|1 genotypes or PS tags (e.g. from a phased caller / read-backed phasing) and the same algorithm yields the single correct diplotype.
Net: skipping phasing never produces a wrong-but-confident single answer for these positions — it produces either an identical answer (when unambiguous) or an honest set of candidates (when ambiguous). The cost is precision, not silent error. The exception is the lowest-function genes, which trade precision for a deliberately conservative single call.

8. Scoring, combinations & special genes

  • Score = specificity. An allele's base score is its count of explicitly-defined (non-null) positions; collapsing a wobble to the reference base subtracts a point, and unexplained "partial" positions subtract too. So between two matching alleles, the one that explains more observed variants wins. This is the "elimination" you intuited, made quantitative.
  • Combination/partial alleles. CombinationMatcher handles a chromosome carrying variants from several alleles (non-overlapping core positions) and flags leftover variants as partials, so novel mixes still get described rather than dropped.
  • Complement validity (isViableComplement()) is what makes it a true diplotype search and not two independent haplotype lookups: the two calls must jointly reproduce the observed het/hom pattern at every position.

9. Can you just download PharmVar CYP1A2 and run it?

This is the real question behind the CYP1A2 page. Short answer: the matcher engine is gene-agnostic and would run on CYP1A2 — but you cannot drop the website table in as-is, and even after you format it, you'd get a diplotype with no clinical meaning. Three distinct problems, in order of severity:

Problem 1 — Coordinates are in the wrong system (a transform, not a blocker)

PharmVar's table lists variants as gene-relative HGVS — 5347T>C, -163C>A, 63C>G (F21L) — counted from the sequence start or the ATG, against NG_061543.1 / NM_000761.5. The matcher needs genomic coordinates: chr15, a GRCh38 position, ref, and alts (because the VCF you genotype is in genomic coordinates).

So you must lift each variant to GRCh38 and emit a variants[] + namedAlleles[] matrix. PharmVar's downloadable package (the Download Gene Data button, not the HTML table) actually ships GRCh37/GRCh38 VCF representations and RefSeqGene mappings, so the conversion is mechanical — but it is a required build step. This is essentially what CPIC/ClinPGx do to produce the _translation.json files PharmCAT ships.

Problem 2 — The suballele tree must be collapsed, and a reference defined

Look at the structure of the page: *1.001 … *1.012, *30.001 … *30.017. These are suballeles (sequence-level subvariants). PharmCAT models one vector per core star allele (*1, *2, …*49), not the whole tree. Two structural traps:

  • Near-ubiquitous tag SNPs. Almost every CYP1A2 allele lists 5347T>C (rs2470890), and many add 5521A>G (rs11636419) — including most *1 suballeles. These are common intronic/UTR tags that do not define function. If you naively make them defining positions, every allele overlaps every other allele and the regex matching can no longer discriminate. CPIC's curation drops or down-weights these; you'd have to too.
  • Nested / subset alleles. *1.002 = just 5347T>C; *30.001 = just -163C>A; *9.001 = -163C>A + 248C>T + tags. Because some alleles' positions are subsets of others, a single sample matches many alleles, and the score (most-specific wins) plus phasing become essential. *9 vs *30 vs *13 all share -163C>A and differ only by an additional coding SNP — so an unphased double-het is genuinely ambiguous here, the §6/§7 problem in full force.

You also need a designated reference allele expressed as actual bases at every position; *1 (PV02647) shows N/A variants on the page (it's the baseline), but you must materialize its base at each modeled position so the "default to reference" step works.

Problem 3 — The clinical layers don't exist for CYP1A2 (the real blocker)

Every single allele on that page reads CPIC Clinical Function: N/A. That is the same reason CYP2C8 isn't in PharmCAT:

  • No phenotypes.json entry ⇒ a called diplotype can't be turned into poor/normal/rapid metabolizer.
  • No CPIC/DPWG/FDA guideline keyed on CYP1A2 ⇒ no drug recommendation to emit.

So even with a perfectly built CYP1A2_translation.json, the matcher would print something like CYP1A2 *1/*1F and then have nothing to say about it. PharmCAT includes a gene only when all three layers exist; CYP1A2 has rich allele data but no actionable function data.

Verdict. The PharmVar CYP1A2 data is the right raw material and the matching algorithm is genuinely gene-agnostic, so "run the same elimination over its star alleles" is conceptually valid. But you cannot use the page directly: you must (1) lift HGVS → GRCh38 VCF coordinates, (2) collapse the suballele tree to core alleles and prune ubiquitous tag SNPs so the vectors stay discriminating, and (3) accept that there is no phenotype/recommendation layer — so you'd get a genotype call with no clinical interpretation. Problems 1–2 are engineering; problem 3 is why it isn't worth shipping.
If you only want the genotype (research, not prescribing), it's very doable: build the translation file from PharmVar's download package (not the HTML), curate the defining vs tag positions, and feed it to the existing matcher unchanged. Expect heavy reliance on phasing for CYP1A2 because so many alleles are distinguished only by combinations of shared SNPs (§7).

10. Checklist to add a new gene

  1. Get PharmVar's download package for the gene (includes GRCh38 VCF + allele table), not the web table.
  2. Pick the reference allele and the set of defining positions (drop ubiquitous non-functional tag SNPs).
  3. Lift every variant to genomic position / ref / alts; build variants[].
  4. For each core star allele, emit the parallel alleles[] vector (null where unconstrained); use IUPAC codes only for genuine wobbles.
  5. Drop the file in definition/alleles/ — the matcher needs no code changes; it will permute, regex-match, complement-check and score automatically.
  6. For clinical output, also supply a phenotypes.json function map and a guideline in prescribing_guidance.json — these do not come from PharmVar (they come from CPIC/DPWG/FDA) and are what's missing for CYP1A2.
